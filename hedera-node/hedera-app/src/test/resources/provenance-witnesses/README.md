# Native provenance witness vectors

`native-v1.json` contains public test vectors for endpoint and EVM verifier integration. The vectors use real native hinTS preprocessing, BLS shares, weighted aggregation, and aggregate verification over synthetic block branches. They represent three adjacent key generations and a separately certified candidate with no signing witness. They are not captured network rotations or a recording of a Solo run.

All keys are deterministic test material generated by `HintsKeyWitnessNativeTest`. Never use them for a live network. No private key material is needed to consume the JSON vectors.

## Contents

- `initialVerificationKeyHex` and `initialTimestampSeconds` define the independently trusted initial checkpoint.
- `generations` records each test generation's verification key and its ordered party weights (party IDs 0, 1, and 2). Generation 4 uses weights `[1, 2, 3]`; the others use `[1, 1, 1]`.
- `certificates` contains the three adjacent predecessor signatures, their source and target keys, and serialized `HintsKeyProvenance` protobufs. Signatures cover only the target VK bytes; construction IDs do not establish trust.
- `witnesses` contains the first and last successor's witnesses. Each includes the canonical encoded timestamp, sibling hash, block signature, reconstructed root, serialized `HintsKeyWitness`, and encoded byte size. The first uses SHA-256 and the last SHA-384 to exercise historical digest support.
- `validBatches` advances the checkpoint in two bounded updates. The second batch includes an intermediate generation without a witness, then verifies the witness for its endpoint.
- `abandonedCandidateCertificate` is a valid signature under the initial key, but has no corresponding signing witness. Committing that candidate must fail. Relabeling a different key's witness with this candidate's construction ID must also fail.
- `rejectedCases` describes mutations that must be rejected by a consumer.
- `rejectedWitnesses` contains serialized negative vectors and the expected verification key for each rejected proof. These include exactly one third of the signing weight under equal and unequal weights, a valid signature over a root with swapped children, and SHA-384 timestamp and same-length sibling mutations that reach cryptographic verification.
- `acceptedWitnesses` includes a single-party signature with weight 3 of total 6. This proves that acceptance counts weight rather than the number of signers.

All byte strings use hexadecimal without `0x`. Integer fields that could otherwise lose precision in JavaScript are decimal strings. Protobuf bytes use the schemas in this repository.

For each witness, reconstruct exactly:

```text
leaf = SHA-256-or-SHA-384(0x00 || timestampProtobufBytes)
root = SHA-256-or-SHA-384(0x02 || leaf || siblingHash)
```

The digest is selected by `hashAlgorithm`. On the protobuf wire, SHA-256 has enum value zero and is omitted: **absent means SHA-256**, independent of the current network digest. SHA-384 has enum value one. The sibling must have exactly the selected digest's length. Verify the block signature under the chain endpoint's VK at the strict greater-than-one-third threshold. This threshold is fixed independently of `tss.signingThresholdDivisor`: a producer configured to stop at less weight may produce an unusable witness. The timestamp leaf is always the left child of the block root. The canonical typed timestamp is encoded with `Timestamp.PROTOBUF`; arbitrary leaf hashes or alternate path positions are not accepted. Construction IDs are unsigned bookkeeping ignored by cryptographic verification; native consensus admission separately requires the ID to name an adopted record.

Only commit a new checkpoint after all predecessor certificates and the endpoint witness verify. Historical timestamps are expected here; the acceptance of a key-catch-up witness must remain separate from freshness checks on a CLPR application message. The reference consumer requires the authenticated witness timestamp to advance beyond the previous committed checkpoint.

For a new consumer with only a trusted key, use `Checkpoint.fromTrustedKey(key)`, which uses epoch as a sentinel lower bound. Never use registration time or the local clock: a consumer registered today must still be able to commit historical endpoints. When restoring a previously committed checkpoint, restore its key and authenticated witness timestamp together. The fixture's initial timestamp is an explicit historical lower bound. Monotonic witness timestamps are an ordering policy; actual key continuity supplies authorization. `HintsKeyProvenanceVerifier` is the reference for endpoint and EVM consumers and is not called by the node runtime.

The two primary witnesses encode to 1,297 and 1,315 bytes with their fixture timestamp nanos of 123. These are example sizes, not fixed wire lengths: nine-digit nanos can add three or four bytes, and other varint fields can also grow. Nanos of 987,654,321 yield 1,301 and 1,319 bytes respectively. JSON hex encoding is not the protobuf byte size.

## Regeneration

From the repository root:

```sh
./gradlew :app:test --tests '*HintsKeyWitnessNativeTest.serializesNativeVectorsForEndpointAndEvmIntegration'
cp hedera-node/hedera-app/build/generated/provenance-witnesses/native-v1.json \
  hedera-node/hedera-app/src/test/resources/provenance-witnesses/native-v1.json
./gradlew :app:test --tests '*HintsKeyWitnessNativeTest'
```

The first command writes `hedera-node/hedera-app/build/generated/provenance-witnesses/native-v1.json`; copy it only when intentionally refreshing the checked-in vectors. JSON keys are sorted for byte-stable regeneration. The full test asserts byte-for-byte equality with the regenerated fixture, verifies all positive and negative serialized vectors independently, and exercises committing accepted batches while preserving the anchor after rejected batches. The native cryptography runtime must be available, as for the existing hinTS library tests. Measure EVM gas using these vectors in the consuming verifier repository; the JVM tests report encoded proof sizes, not an EVM gas estimate.
