## Scope

This is a **deliberately narrow, socket-only** first pass over the `04-07-2026` cluster artifact. It extracts **only**:

1. **Socket memory** from the passive `ss -tinm` samplers — the `-m` flag adds the `skmem:(...)` block, i.e. per-socket kernel memory accounting.
2. **`SocketFactory` logging** from each node `swirlds.log` — the configured socket buffer sizes.

It does **not** perform the full artifact-processing protocol (no reconnect-timing/counter/workload/state calibration extraction, no per-run protocol files, no `verification-notes.md`/`batch-summary.md`, no manifest entry). Those wait for an explicit request to do the full pass.

Coverage of the socket evidence is **all 7 nodes × all 3 runs**, with `skmem` **bounded to each learner's receiver-reconnect window**.

## Method

- Learner (`network-node1` / nodeId 0) receiver-reconnect windows were anchored from `swirlds.log` (`ReconnectStatePeerProtocol` start/finish payloads + `Now in ACTIVE`).
- `skmem` was bounded to `[first receiver-reconnect start, last defined-iteration receiver-reconnect finish]` using timestamp-gated `awk`/`python` over the samplers; a short idle baseline before/after was sampled for contrast.
- Pod → local-IP maps were built from each sampler's own `ss` local address (the sampler filename identifies the pod); teacher IPs come from `otherNodeId` per iteration.
- Every value carries a run-root-relative source reference. Extraction and verification used **separate** agents; `ss` `send`/`pacing_rate`/`delivery_rate` are treated as observed socket behaviour only, **never** as link capacity.

### `skmem` field legend

```text
skmem:(r<rmem_alloc>,rb<rcv_buf>,t<wmem_alloc>,tb<snd_buf>,f<fwd_alloc>,w<wmem_queued>,o<opt_mem>,bl<back_log>,d<sock_drops>)
  r   rmem_alloc  bytes currently allocated to the receive buffer
  rb  rcv_buf     receive buffer cap (SO_RCVBUF); kernel-autotuned, starts at 65536
  t   wmem_alloc  bytes currently allocated to the send buffer
  tb  snd_buf     send buffer cap (SO_SNDBUF); kernel-autotuned, starts at 87040
  f   fwd_alloc   forward-allocated (pre-charged) memory
  w   wmem_queued bytes queued in the send buffer but not yet sent/acked
  o   opt_mem     option memory
  bl  back_log    socket backlog bytes
  d   sock_drops  cumulative dropped packets on this socket (monotonic per socket)
```

`SocketFactory` logs the **configured** `SO_RCVBUF`/`SO_SNDBUF` = **32768**. The Linux kernel reports the rounded/doubled floor of that as `rb65536`/`tb87040` in an idle socket, then **autotunes upward** under load. The gap between the configured 32768 and the multi-MB `rb`/`tb` observed during reconnect is the central socket-memory finding below.

## Key Findings (cross-run)

1. **Configured socket buffers are tiny and uniform.** Every node in every run logs `SocketFactory` server-receive, client-receive, and client-send buffers = **32768 bytes**. No node reports any other value; no `SocketFactory` exception/reset/timeout lines appear anywhere. Idle sockets sit at the kernel floor `rb65536`/`tb87040`.

2. **The kernel autotunes buffers far above the configured 32768 during reconnect.** On the active learner↔teacher socket(s), `rb` (receive cap) and `tb` (send cap) climb into the **multi-megabyte** range while the configured value stays 32768. Examples (window-bounded, verified): top-to-bottom learner `rb` up to **5,753,152** / `tb` **2,132,480**; two-phase learner `rb` up to **22,472,504**; parallel-sync learner→teacher `tb` up to **4,665,344**. So the configured 32768 is **not** the effective in-flight ceiling — the kernel is.

3. **Real send-side backpressure and queue buildup are present on the reconnect socket.** The learner↔teacher socket shows large `Send-Q`/`notsent`/`wmem_queued` (MB-scale), non-zero `rwnd_limited` time, and non-trivial cumulative `drops` — i.e. the reconnect data path is buffer/window-bound at times, not latency-idle. This is the strongest signal so far that local `networkInflightBytesLimit` should model a **real, large-but-finite** in-flight cap rather than a tiny 32 KB cap or an unbounded one.

4. **Intra-cluster RTT is very low.** `minrtt` on the reconnect sockets is sub-millisecond in the two Dallas-colocated runs (~40–80 µs) and ~7–10 ms in parallel-sync (`dallas4`), consistent with same-DC pod-to-pod links. (Reported as socket RTT evidence only; see calibration caveats.)

## Critical Coverage Caveats

These bound how far the socket evidence can be trusted per run. They are recorded here, in the per-run sections, and in the Coverage Register.

- **two-phase-pessimistic (`dallas12`): huge ACTIVE gap + sampler stops early.** The learner reaches `ACTIVE` only at **2026-07-04T04:57:09.719Z**, ~3h13m after the last of the four defined receiver-reconnect iterations finished (01:43:55.701Z). Receiver reconnect cycles actually continue well past iter4 (28 start/finish cycles total, into ~03:53Z). All 7 samplers **stop at 02:46:58Z**, so `skmem` covers the four-iteration window fully but **not** the later reconnects or the ACTIVE marker. Treat this run's socket data as covering the *defined iteration window only*; the ACTIVE gap suggests platform instability that a full-pass network-disease preflight must adjudicate before any calibration use.
- **parallel-sync (`dallas4`): samplers miss almost the entire reconnect.** iter1 alone ran ~3h13m (02:41:09 → 05:54:58). Every sampler captures only **02:35:05Z → 02:51:48Z (~16m40s)** and then stops (process killed while reconnect continued ~3.5h more). So `skmem` exists for **only the first ~10.5 min of iter1**; iters 2–4 (and two further post-iter4 reconnects through 06:20:24, before ACTIVE 06:20:45) have **zero** sampler coverage. Also `network-node4` (nodeId 3) and `network-node6` (nodeId 5) have **no `swirlds.log`** (SocketFactory unconfirmable there).
- **top-to-bottom (`dallas11`): clean.** All 7 samplers span the full reconnect window; ACTIVE is a normal +4m after the last finish.
- **`network-node7` (nodeId 6) logs only the server-receive `SocketFactory` line** (no client sockets initiated) in all three runs — expected, recorded as `partial` for that node, not an error.
